That’s a doable project. Here’s how I’d approach it, plus one issue with the YouTube plan that’s worth settling early.

The YouTube download idea

Downloading music from YouTube and serving it to users violates YouTube’s Terms of Service and, for copyrighted songs, is copyright infringement. In practice:

Apple’s App Store and Google Play will reject or pull the app. Apps built on this model get removed regularly.
It’s fragile. Pytube is largely unmaintained and breaks often. yt-dlp is the actively maintained alternative, but YouTube keeps changing things, and server IPs get blocked.
Spotify’s files are DRM-encrypted, which is why you haven’t found a clean way to get them.

For a personal learning project that only you use, people do this. For something you’d share or publish, I’d use a legal source instead:

Your own music library (files you own), which is how Navidrome and Jellyfin work. Your server streams them to your app.
Free or open catalogs like Jamendo, Audius, Free Music Archive, and the Internet Archive.
Licensed SDKs like Apple MusicKit, though these generally don’t allow you to host or download the audio yourself.

The nice part is that the architecture is the same either way. Only the “where do the audio files come from” module changes, so you can build everything else now.

Suggested stack

Mobile app: React Native (not plain React). React alone is for the web. React Native with Expo gives you one codebase for Android and iOS.

react-native-track-player for playback, background audio, and lock-screen controls
expo-file-system for offline downloads
expo-sqlite or WatermelonDB for locally stored playlists and download metadata
React Query for server data

Server: FastAPI (Python).

PostgreSQL for users, tracks, playlists, and listening history
Audio files in S3-compatible storage or on disk, served with HTTP range requests so seeking and streaming work
JWT auth
A background worker (Celery or RQ) for ingesting and processing audio

Recommendations: this is the part you build in stages.

Log implicit feedback (plays, skips, completions, likes).
Start simple with “popular among similar users,” or similarity on track metadata and tags.
Move to collaborative filtering (the implicit library works well), then optionally audio embeddings for content-based similarity.

Weighing how to help with downloading music for personal use.

Fair enough, that’s your call, and a private server for you and your friends is a much simpler situation. Here’s how I’d set it up.

Use yt-dlp instead of pytube

Pytube breaks constantly. yt-dlp is actively maintained, can search YouTube directly, and extracts audio and metadata in one step.

python
# ingest.py
import yt_dlp
from pathlib import Path

MUSIC_DIR = Path("media")
MUSIC_DIR.mkdir(exist_ok=True)

def search(query: str, limit: int = 10):
    opts = {"quiet": True, "extract_flat": True}
    with yt_dlp.YoutubeDL(opts) as ydl:
        info = ydl.extract_info(f"ytsearch{limit}:{query}", download=False)
    return [
        {"id": e["id"], "title": e["title"], "channel": e.get("channel"),
         "duration": e.get("duration")}
        for e in info["entries"]
    ]

def download(video_id: str) -> dict:
    opts = {
        "format": "bestaudio/best",
        "outtmpl": str(MUSIC_DIR / "%(id)s.%(ext)s"),
        "postprocessors": [{
            "key": "FFmpegExtractAudio",
            "preferredcodec": "m4a",   # plays natively on both iOS and Android
        }],
        "quiet": True,
    }
    with yt_dlp.YoutubeDL(opts) as ydl:
        info = ydl.extract_info(f"https://youtube.com/watch?v={video_id}", download=True)
    return {"id": video_id, "title": info["title"], "artist": info.get("artist") or info.get("uploader"),
            "duration": info["duration"], "thumbnail": info.get("thumbnail"),
            "path": f"{video_id}.m4a"}

You’ll need ffmpeg installed on the server.

Streaming endpoint
python
# main.py
from fastapi import FastAPI, HTTPException
from fastapi.responses import FileResponse
from pathlib import Path

app = FastAPI()

@app.get("/tracks/{track_id}/stream")
def stream(track_id: str):
    path = Path("media") / f"{track_id}.m4a"
    if not path.exists():
        raise HTTPException(404)
    return FileResponse(path, media_type="audio/mp4")

Recent Starlette versions handle HTTP range requests in FileResponse, which is what makes seeking work in the player. Test seeking early. If it doesn’t work, upgrade Starlette or write a small range handler.

Practical tips for this setup
Download once, serve forever. Cache every track on your server the first time anyone requests it. Your database then becomes a growing shared library, and later plays never touch YouTube.
Run the server at home (a Raspberry Pi, an old PC, or a NAS) with Tailscale so your friends can connect without port forwarding. Datacenter IPs on cheap VPSes get blocked by YouTube much more often than residential ones.
Keep yt-dlp updated (pip install -U yt-dlp). When downloads suddenly fail, this is usually the fix. Automate it with a weekly cron job.
Do downloads in a background job and return a status to the app, since a download takes several seconds. FastAPI’s BackgroundTasks is fine to start with, and you can add a queue later.
Add auth early. Simple JWT login with invite-only registration keeps strangers off your server.

This is a good set of screens, and it all fits the plan. There’s one naming issue to settle first, because it changes how Library works.

“Library” now means the phone

Until now, “library” meant the songs on your server. You’ve redefined it as the songs downloaded to the phone. Those are different things, so I’ll use these terms:

Server cache: audio your server has fetched. It’s invisible plumbing the user never browses.
Library tab: songs saved on the phone, playable with no server.

This means the Library tab can’t exist until phone downloads exist (Stage 9 below). Until then, the small server list at the bottom of your screen is a stand-in.

The screen map
Discover: search and tap to stream (what you have now), later with a download button and YouTube playlist import.
Playlists: your playlists, and inside one, its track list.
Library: downloaded songs.
Mini player: a bar above the tab bar, always visible while something is loaded.
Full player: opens when you tap the mini player, with a big thumbnail, a seek bar, and previous/play/next.
The key architecture idea: one player above all the screens

If each screen owned its own player, music would stop when you switch tabs. Instead, a PlayerProvider (a React Context) sits at the top of the app. Every screen and the mini player read from it. This is the biggest new React concept coming up (context and custom hooks), and everything else depends on it.

State it holds: the queue (a list of tracks), the current index, whether it’s playing, and the position and duration.

Functions it exposes:

playQueue(tracks, startIndex): the one entry point for playing. Tapping a row in any list calls it with that list, so “next” always means the next row in the list you tapped from.
togglePlay()
next() and previous(): move the index and load that track. A common convention is that previous restarts the current song if you’re more than a few seconds in.
seekTo(seconds)
Auto-advance: an effect that watches for the track finishing and calls next().
resolveSource(track): returns the local file path if the track is downloaded, otherwise the server stream URL. Putting this in one function is what makes offline playback easy later.
Other shared modules

Split App.tsx into files. A suggested layout:

src/
  api.ts            # search(), ingest(), getTracks(), playlist calls
  types.ts          # Track, Playlist
  player/PlayerProvider.tsx
  downloads/        # later: downloadTrack, isDownloaded, deleteDownload, listDownloads
  components/       # TrackRow, MiniPlayer
  screens/          # Discover, Playlists, Library, Player

Putting every fetch in api.ts means a server address change or an auth header (accounts, later) is a one-file edit.

What each piece needs

Playlists (server side first). Two tables: playlists (id, name, created_at) and playlist_tracks (playlist_id, track_id, position). Routes: list playlists, create, get one with its tracks, add a track, remove a track. Reordering and per-user ownership come later. The test is the same as before: build it and try it in /docs before touching the app.

Phone downloads (Library). Two parts: files saved with Expo’s file system module, and a small local database (expo-sqlite) recording each download’s id, title, artist, duration, thumbnail, and file path. The Library screen reads that table. Functions: downloadTrack, isDownloaded, deleteDownload, listDownloads. Check the current expo-file-system docs first, because its API changed in recent SDKs.

YouTube playlist import. The server uses yt-dlp to list a playlist’s entries, creates a playlist, and ingests tracks. A 50-song playlist can’t be done in one request, so it needs a background job with status polling. That’s the right moment to build the async design you asked about earlier, so it comes after the basics.

Navigation. The blank template has none. Look at React Navigation’s bottom tabs (explicit code, easier to learn from) or expo-router (file-based). I’d start with React Navigation and read its docs first, since setup steps change.

Local playlists simplify things. The server needs no playlist tables or routes, and all of that work moves into the app.

What local playlists mean for the design

The phone needs its own database (expo-sqlite, which works in Expo Go). You already know SQL from db.py, so this part will feel familiar. One local schema covers playlists, downloads, and the Library tab:

tracks: id, title, artist, duration, thumbnail, file_path (null until downloaded), downloaded_at
playlists: id, name, created_at
playlist_tracks: playlist_id, track_id, position

Playlists must store track metadata locally, not only ids. Otherwise a playlist row couldn’t show a title or thumbnail without asking the server, and it would break if the server were off. A track row exists once it’s in any playlist or downloaded, and file_path says whether the audio is on the phone.

One function decides where audio comes from

resolveSource(track) tries these in order:

file_path is set, so play the local file.
Otherwise, play the server stream URL.
If the server doesn’t have the file, call /ingest. It takes an id and fetches from YouTube, so playlists keep working even if the server cache is ever cleaned up.

This is why storing only the YouTube id and metadata in playlists is enough.

Library tab: two sources, with search

Library gets a switch between On phone and On server, plus a search box.

On phone: a query against the local tracks table where file_path is not null, filtered with LIKE on title and artist. No server involved, so it works offline.
On server: a new server route. Extend GET /tracks with an optional q query parameter. When present, filter with WHERE title LIKE ? OR artist LIKE ?, using ? placeholders and % added to the value in Python, never an f-string. Tapping a server track plays it, and a button saves it to the phone.

Since your friends will share this server, the “On server” view will show everything anyone has downloaded. For a private group that’s probably a feature.

YouTube playlist import gets easier

The server only needs a route that lists a playlist’s entries with yt-dlp’s flat extraction, which is fast and returns metadata with no audio. The app creates a local playlist from it right away. Audio is fetched when you play or download a track, one at a time. So the import doesn’t need a background job. Only a “download all” button would, and that can come later.

What you lose

Playlists live only on that phone. They won’t sync between your devices or between friends, and if you uninstall the app or clear its data, they’re gone. An export/import button later would cover the backup case, and it’s an easy add-on.
